# 桌宠小窗拖拽问题排查记录

> 日期：2026-11-25　｜　项目：DSH 游戏副驾插件
> 修复已包含在本仓库的 `plugin/runtime/overlay/main.mjs` 中。

---

## 一、一句话结论

**不是拖拽坐标算法的问题，是 Electron 20 + Windows 的透明无边框窗口每调用一次 `win.setPosition()`，窗口宽高就悄悄 +~1.3px。** 用户拖几百帧，窗口尺寸膨胀上千像素，宠物在窗口内相对位置持续漂移，视觉上就是“长按往下掉 / 越拖越偏”。修复方式：所有挪窗统一改用 `win.setBounds()` 并显式带上固定宽高，绝不单独调用 `setPosition()`。

---

## 二、现象与排查时间线

用户在同一问题上连续反馈了五轮，每一轮的“修复”都只覆盖了表面：

| 轮次 | 现象 | 当时判断与改动 | 实际结果 |
|---|---|---|---|
| 1 | 小窗偶尔拖不动 | `mousedown` 没有 `pointerId`，`setPointerCapture(undefined)` 被静默吞掉 → 改 Pointer Events | 捕获生效，偶发拖不动解决 |
| 2 | 长按不动时窗口自己朝一个方向漂移 | 每帧读全局光标做绝对定位，手抖/光标 warp 被累积 → 改逐帧增量累加 | 长按漂移缓解 |
| 3 | 快速甩动时指针和窗口有偏移 | 单帧位移被阈值整帧丢弃 → 阈值 200→800→3000 并补 pointerup 尾段 | 偏移变小但仍有 |
| 4 | 晃动鼠标后窗口只往右/下偏 | 增量累加会永久保留每帧残差 → 改纯函数绝对定位（光标回原点窗口必回原点） | 坐标层确实修对了，物理晃动回原点零残差 |
| 5 | **长按又会直接往下掉** | 回归排查 → 发现窗口尺寸在膨胀，与坐标算法无关 | 真正根治 |

前三轮的共同问题：都在“坐标怎么算”里打转，没有检查**窗口尺寸本身有没有变**。

---

## 三、证据链

### 3.1 现场日志（决定性线索）

小窗主进程日志：`%TEMP%\dsh-game-pet-window.log`（环境变量 `GP_LOG_FILE` 指定）。
每 15 秒有一行 `state ... bounds={...}`，把最近一次用户操作前后的数据拉出来：

```
06:09:15 drag start at 1844,984.8 window 1665,709
06:09:19 state bounds={"x":1013,"y":133,"width":648,"height":663}
06:09:21 drag end -> 1013,130
06:09:22 drag start at 1479.2,912 window 1013,130
06:09:34 state bounds={"x":850,"y":-368,"width":1006,"height":1031}
06:09:47 drag start at 1351.2,584.8 window 850,-368
06:10:04 state bounds={"x":748,"y":-624,"width":1216,"height":1341}
```

初始尺寸是 344×363（日志 `initial bounds` / `page-probe winSize` 均可印证）。也就是说，**在一次拖拽过程中窗口被放大了 3.5 倍**，同时左上角被推到屏幕外。保存的位置文件 `%USERPROFILE%\.dsh\dsh-game-pet-window.json` 也写入了坏坐标 `{"x":748,"y":-624}`。

> 关键判断：如果用户只是“坐标算错”，bounds 的 `width/height` 不应该变。尺寸在涨，说明问题不在坐标公式。

### 3.2 隔离实验（定位根因）

写一个独立的最小 Electron 程序，不加载任何插件代码，只创建同款窗口：

```js
new BrowserWindow({
  width: 340, height: 360, x: 1665, y: 709,
  frame: false, transparent: true, resizable: false,
  alwaysOnTop: true, focusable: false,
});
```

然后每 40ms 调一次 `win.setPosition(x, y)`，共 60 帧，模拟拖拽：

```
start    {"x":1664,"y":708,"width":344,"height":363}
step 10  {"x":1464,"y":608,"width":357,"height":376}
step 20  {"x":1264,"y":508,"width":371,"height":389}
step 40  {"x":864, "y":308,"width":397,"height":416}
step 60  {"x":464, "y":108,"width":424,"height":443}
```

**纯 `setPosition` 就能复现膨胀**，约 +1.3px/帧。位置本身是对的，错的只有尺寸——与插件逻辑无关。

同一实验改为 `win.setBounds({x, y, width, height})` 并固定宽高：

```
start    {"x":1664,"y":708,"width":344,"height":363}
step 10  {"x":1464,"y":608,"width":345,"height":364}
step 60  {"x":464, "y":108,"width":345,"height":364}
```

尺寸从第 1 帧起稳定，之后 60 帧不再增长（344↔345 的 1px 是 Windows 像素对齐波动，不可累积）。根因坐实。

## 四、根因分析

- Electron 20 在 Windows 上处理 `frame:false` + `transparent:true` 的无边框窗口时，`setPosition()` 内部改动窗口位置的同时会按某种 DIP/物理像素换算重新计算 bounds，宽高被反复放大。`resizable:false` 也挡不住。
- 拖拽期间 `pointermove` 每触发一次，主进程就调一次 `setPosition()`；一次拖拽几百帧，膨胀就累积到几百上千像素。
- 窗口变大时，页面内的宠物素材是按百分比布局的，宠物相对窗口和屏幕的位置随之改变，用户看到的就是“按住不放，宠物自己往下掉 / 越拖越偏”。
- 这也解释了为什么之前的“晃动一圈回原点零残差”验证会通过却仍有问题：**坐标确实算对了，但窗口的尺寸在同时被系统偷改**，两类问题叠加。

---

## 五、修复方案

改动集中在 `plugin/runtime/overlay/main.mjs`：

1. 在 `createWindow()` 后立即记录窗口外框尺寸：

```js
const initialBounds = win.getBounds();
winBoundsSize = { width: initialBounds.width, height: initialBounds.height };
```

2. 新增统一的挪窗入口，任何位置变更都带上固定宽高：

```js
function placeWindow(x, y) {
  if (!win) return;
  const w = winBoundsSize?.width;
  const h = winBoundsSize?.height;
  if (!w || !h) {
    win.setPosition(Math.round(x), Math.round(y));
    return;
  }
  win.setBounds({ x: Math.round(x), y: Math.round(y), width: w, height: h });
}
```

3. `moveDrag()` 和 IPC `gp-set-position`（恢复默认位置）都改为调用 `placeWindow()`；渲染层 `overlay.html` 与 `preload.cjs` 不需要改动——它们上报的绝对屏幕坐标本来就是对的。

4. 保留上一轮已修好的绝对定位、死区、warp 平移基准机制；新增 400ms 节流的 `drag move` 日志，直接打印光标坐标、相对偏移和窗口真实 bounds，便于以后一眼分辨“坐标错”还是“尺寸错”。

## 六、验证

1. **语法检查**：`node --check main.mjs` 通过。
2. **隔离实验**：`setBounds` 连续 60 帧尺寸恒定，见 §3.2。
3. **真实主进程长跑**：直接加载正式 `main.mjs`，从主进程按 40ms 一帧注入 300 帧拖拽事件，共 12 秒：
   - 全程记录的 bounds 只有 `344×364` 和 `345×364` 两种取值，无累积膨胀；
   - 同步快跑的一次终点为 `764,108`，与公式 `1664 - 300×3 = 764`、`708 - 300×2 = 108` 完全一致。
4. **收尾**：修复已合入本仓库；私有开发仓库里的提交哈希与分发包路径与公开使用无关，此处略去；临时验证程序已清理。

> 用户侧生效方式：重启 DSH。旧窗口尺寸已损坏且位于屏幕外，重启后 `visiblePosition()` 检测到与所有显示器都无足够交集，会自动回到默认右下角。

## 七、方法论教训（可复用）

1. **现象描述不等于故障定位**。用户说“拖不动 / 往下掉 / 偏移”，必须先落到可观测数据（日志里的坐标、尺寸、时长）再动手，否则容易连续几轮修错对象。
2. **先看尺寸，再看坐标**。窗口类问题排查三件套：`getBounds()` 的 `x/y` 是否跟随、`width/height` 是否恒定、`moved` 事件是否触发。尺寸在变就不要再调坐标阈值。
3. **隔离实验优先**。怀疑某个 API 有副作用时，写一个不依赖业务代码的最小程序反复调用它 60 帧，比在完整系统里猜测快得多，也更能说服人。
4. **警惕假阳性验证**。之前用合成事件自测等于“自己考自己”；物理鼠标模拟时如果日志里没有 `drag start`，说明鼠标压根没进入命中区，“窗口没动”不能证明任何事。验证必须确认关键事件真的触发。
5. **日志要能区分故障类型**。这次给 `drag move` 加了真实 bounds 输出，下次同类问题不用再做隔离实验就能从日志直接区分“坐标错”和“尺寸错”。
6. **改动前先确认版本来源**。整轮排查都通过进程命令行确认 DSH 实际加载的是正在修改的那份 `main.mjs`，避免“改了代码但跑的是旧版本”。
